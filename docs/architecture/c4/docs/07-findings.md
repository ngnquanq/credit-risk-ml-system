# 7. Findings

These are the places where the built system departs from what the architecture implies. Each is tagged on the affected element or relationship in `workspace.dsl` (`Risk` = red outline, `Gap` = dashed red), so they show on every diagram.

Severity: **High** = wrong decisions or lost applications. **Medium** = throughput, availability or operability. **Low** = hygiene.

| ID | Sev | Finding | Element(s) | Evidence | Fix |
|---|---|---|---|---|---|
| F-01 | High | `DAYS_EMPLOYED` is served with the opposite sign to training. Kaggle values are negative, with `365243` meaning unemployed or pensioner. The UDF returns `created - start`, which is positive. Positive values only occur for the sentinel in training, so live applicants probably fall into the unemployed/pensioner branch of the trees. | Flink › CDC UDFs | `application/flink/jobs/cdc_udfs.py:139` | Return `(start - created).days`, emit `365243` when there is no employment date, and add a parity test against `application_train`. |
| F-02 | High | Bureau features have two implementations: dbt SQL for training and a Python UDF for serving. Nothing checks that they agree. | Flink › Bureau aggregation UDF; dbt › Mart models | `ml_data_mart/models/mart/mart_bureau_features.sql:70` vs `application/flink/jobs/bureau_aggregation_udfs.py:257` | Pick one source of truth (for example, have the bureau service read `mart_bureau_features` the same way the DWH service reads the marts), or add a golden-file parity test for N ids. |
| F-03 | High | **Dual write.** The API publishes `{sk_id_curr, type}` straight onto the Debezium topic. The bureau and DWH services accept it, so every application is fetched twice, and the completeness check then emits `feature_ready` more than once, so applications are scored 1–3 times. | API › KafkaScoringGateway; Feast › Readiness publisher | `application/core/config.py:75`, `infrastructure/external/kafka_scoring.py`, `feast_repo/stream_processor.py:289` | Delete the publish, since CDC is the outbox. Make readiness fire once (for example `SADD` returns 1 only on the transition to 3: check `SCARD` before and after, or use `SET NX` on a `ready:<id>` key). |
| F-04 | High | **The decision loop is open.** Nothing consumes `hc.scoring`, nothing writes `application_status_log`, and `GET /status` always returns 404. (The broken, unused `get_by_id()` repository method was deleted on 2026-11-21.) | Decision consumer (Gap); API routes; PostgresLoanRepository | `schemas/002_create_application_status_log.sql` | Add a decision consumer that writes `application_status_log` (`SCORED`/`UNDER_REVIEW`) idempotently by `(sk_id_curr, model_version)`, and have `GET /status` read it. |
| F-05 | Medium | A new Kafka producer per HTTP request, never flushed. That adds connection setup to every request, and queued messages can be lost when the object is garbage-collected. | API › Dependency wiring | `entrypoints/api/dependencies.py:16-20` | Moot once F-03 is fixed. Otherwise use one producer per process created at lifespan startup, with `flush()` on shutdown. |
| F-06 | High | **At-most-once processing.** The bureau, DWH and Feast consumers auto-commit offsets on a timer and drop on error, with no retry or DLQ. Feast additionally buffers rows in memory before writing. A crash or a ClickHouse error silently loses applications. | Bureau / DWH › Batch consume loop; Feast › consumer threads, buffers | `bureau_consumer.py:49-50`, `feature_consumer.py:48-49`, `stream_processor.py:375-376` | `enable.auto.commit=false`, commit after produce or write succeeds, a bounded retry, then a per-stage DLQ. Bound the executor queue. |
| F-07 | High | **The training/serving feature contract is broken for the 24-feature model.** `CODE_GENDER` is a model input but no Feast view provides it (the Flink sink drops it). The predictor's startup validation therefore raises and refuses to serve this model. **Gender is also a protected attribute in credit decisions**, so it should not be a model input at all. | Flink › CDC job; Scoring › Model loader | `feast_repo/feature_schema/*.json` (no `code_gender`), `cdc_application_etl.py` sink DDL, `scoring/service.py` startup validation | **Do not add gender to serving.** Drop `CODE_GENDER` from the model features and retrain; keep it only in an access-restricted offline set for bias audits (disparate impact ratio, four-fifths rule; NIST AI 100-1 §3.7, MEASURE 2.11) and check for proxies. Add a CI check that `feast_metadata.selected_features ⊆ Feast views` before a model is registered. |
| F-08 | Medium | **The Kubeflow path trains a different model.** The snapshot is `mart_application` + `TARGET` only (no bureau or history), and `train_and_register` uses every column, including `SK_ID_CURR`, as a feature. | Training pipeline › train_and_register; Training snapshot store | `Makefile:197-205`, `services/model-lifecycle/pipeline/pipeline.py:385` | Export the same 24-feature dataset the local path uses, with an explicit feature list, and drop the entity key. |
| F-09 | Medium | **Per-applicant ClickHouse lookups are full scans.** Tables are `MergeTree ORDER BY tuple()`, so `WHERE SK_ID_CURR = ?` scans `bureau` (~1.7M rows) and `bureau_balance` (~27M rows) on every application. This is a likely cause of the 85.9% CFS throttling measured in load-test cycle 0. | Bureau store | `platform/data/k8s/data-warehouse/02-clickhouse-init.yaml:161` | `ORDER BY SK_ID_CURR` (and `SK_ID_BUREAU` for balances), or pre-aggregate per customer in dbt and look up one row. |
| F-10 | Medium | The scoring service builds a new `FeatureStore` (and so loads `registry.db` from MinIO) on every request. This adds latency on the path the load test identified as the bottleneck. Not yet measured. | Scoring › Feature fetcher | `application/scoring/service.py:482` | Build it once at startup and cache it. `feast_fetch_ms` in `score_by_id_timing` will show the effect. |
| F-11 | Medium | **Measured throughput limit** in KafkaChannel → KServe delivery: ~4k lag on the channel subscriber group, 502s and queue-proxy connection resets, 17.5% completion in a 3-minute window. Partition counts cap parallelism (8 KafkaSource consumers on 4 partitions; HPA max 6 on 4-partition topics). | Scoring sequence; Feature-ready event source | `tests/test_load/RESULTS.md`, `platform/ml/k8s/kserve/kafka-source.yaml:14`, `04-kafka-init.yaml:20` | Fix F-10 first. Then try the KafkaSource → InferenceService directly (a one-step Sequence adds a channel hop), raise topic partitions, and tune queue-proxy concurrency. |
| F-12 | Medium | **Serving watcher rollout logic.** Deployed versions are held in memory, so after a restart every target version is rebuilt. The Sequence is pointed at the *last version processed in set iteration order*, not necessarily the newest. Cut-over is immediate, with no canary and no rollback. | Serving watcher | `services/model-lifecycle/serving-watcher/watcher.py:407-418` | Point at `max(target_versions)`, derive state from existing InferenceServices, and gate the Sequence patch on the new ISVC being `Ready`. |
| F-13 | Medium | Flink has no checkpointing, so source offsets are never committed. After a job restart, `earliest-offset` replays the whole CDC topic, and every application re-enters the pipeline and is re-scored. | Stream processing cluster | no `execution.checkpointing.*` in `platform/data/k8s/stream-processing/` or the jobs | Enable checkpointing (exactly-once for `upsert-kafka`) with a state backend on a PVC or MinIO. |
| F-14 | Medium | Single points of failure: one Kafka broker with RF 1, one Redis without persistence, one ClickHouse, one KafkaChannel dispatcher. | Event broker; Online store; ClickHouse; Scoring sequence | manifests | Acceptable for a single-node demo, but state it as a non-goal. In production: 3 brokers, RF 3, `min.insync.replicas=2`; Redis with AOF or a replica. |
| F-15 | Medium | Incomplete applications disappear silently: if one source is late by more than 300 s, or failed (F-06), the coordination key expires and no event, metric or log marks it. | Feast › Completeness coordinator | `stream_processor.py:95` | Use keyspace notifications or a sweeper that emits `feature_timeout` (decision `under-review`) for expired keys. |
| F-16 | Medium | **Promotions build scoring code from a feature branch**, `feature/the-grand-migration`, not `master`. What runs in production is therefore not what is on the default branch. | Bento builder job; Promotion watcher | `services/model-lifecycle/mlflow-watcher/builder-configmap.yaml:31-34` | Pin `APP_REF` to the commit SHA that trained the model (log it as an MLflow tag). |
| F-17 | Low | Security posture: the API has no authentication or authorisation, CORS allows all methods and headers with credentials, Kafka is PLAINTEXT, and highly sensitive documents sit in MinIO with no lifecycle policy. Model input examples containing applicant data are stored in MLflow. | API; Document object store; Event broker; MLflow | `entrypoints/api/main.py` (CORS), manifests | Listed as future work. At least drop `input_example`, add bucket lifecycle rules, and use NetworkPolicies. |
| F-18 | Low | Documentation drift: `system-overview.md` shows Flink writing to Redis and ClickHouse (it writes neither). ADR-0006 is referenced but missing. (The old scan report and status logs were moved to `docs/history/` on 2026-11-21.) Jaeger has no Makefile target even though every service exports traces to it. | Trace collector; docs | `docs/architecture/system-overview.md`, `isvc-template.yaml`, `scoring/service.py:739` | Point `system-overview.md` at this model; add `k8s-tracing`. |

## Suggested order of work

1. **F-07, F-01** together: drop `CODE_GENDER` and retrain, and fix the `DAYS_EMPLOYED` sign. Without them the 24-feature model either cannot start or scores everyone as unemployed. Then **F-02** (parity test).
2. **F-03, F-04**. Remove the dual write, make readiness fire once, and close the loop so a decision reaches PostgreSQL and the API.
3. **F-06, F-15, F-13** (delivery guarantees), then **F-09, F-10, F-11** (throughput), re-running `run_e2e_load_test.sh` after each change.
4. **F-12, F-16** (safe rollouts), then the rest.
