## What makes it different

<CardGrid>
  <Card title="Decisions, not just scores" icon="approve-check">
    A three-band policy (approve, review, reject) and an idempotent decision recorder. When features are missing or scoring fails, the system never approves automatically: it routes the application to a person.
  </Card>
  <Card title="Explanations for each audience" icon="comment">
    Reasons come from SHAP and are mapped through a feature catalog. Applicants read plain-language reasons. Underwriters see the score and each feature's contribution. Loan officers never see weights they could coach against.
  </Card>
  <Card title="Fairness by construction" icon="setting">
    A versioned feature catalog tags protected attributes and their proxies. Training refuses a feature set that uses them unless the set is explicitly marked legacy.
  </Card>
  <Card title="Security and audit as features" icon="seti:lock">
    Two Keycloak realms, a permission matrix as code, maker–checker reviews, and four-eyes changes to the decision policy. Personal data is encrypted per field and kept out of the event stream, and every access lands in a hash-chained audit trail.
  </Card>
</CardGrid>

## The pipeline in one picture

<pre class="mermaid">{`flowchart LR
  A[Applicant or loan officer] --> P[Portals · Next.js BFF]

  API --> PG[(PostgreSQL)]
  PG -- CDC --> K[[Kafka]]
  K --> F[Flink feature jobs]
  F --> FS[(Feast · Redis)]
  FS --> S[Scoring · KServe + XGBoost]
  S --> D[Decision recorder]
  D --> PG
  D --> R[Underwriter review]`}</pre>
