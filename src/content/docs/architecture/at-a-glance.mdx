A loan application becomes a decision in a chain of small, independent steps connected by events. This page shows the chain once. The pages after it zoom in, one level at a time, and you can stop at whatever depth you need.

## The system in one picture

<pre class="mermaid">{`flowchart LR
  P[Portals] --> API[Loan API] --> DB[(Database)] --> FE["ETL pipelines<br/>for features creation"] --> SC["Feature store<br/>and scoring"] --> REC["Decision<br/>recorder"]
  REC --> DB
  REC -. "only if the score is in the review band" .-> UW["Manual<br/>review"]
  classDef added fill:#fdecee,stroke:#c8102e,color:#111;
  class P,REC,UW added;`}</pre>

Solid white boxes are the original pipeline: application intake, change-data capture, streaming feature engineering, feature store and model scoring. Red boxes were added by the release-readiness work: portals, the decision recorder and manual review. The dashed line means a condition: only an application whose score falls in the review band (0.25 to 0.35), or whose features are missing, goes to a person. The others are approved or rejected automatically. They have manifests and tests and run in the local stack; they have not yet been deployed with the rest on the cluster.

## The event chain in text

```text
Loan application -> PostgreSQL -> Debezium (CDC) -> Kafka hc.applications.public.loan_applications
  |- Flink CDC job ----------------------------------> hc.application_features
  |- bureau service (ClickHouse) -> hc.application_ext_raw -> Flink bureau job -> hc.application_ext
  '- DWH service (ClickHouse marts) -----------------> hc.application_dwh
       -> Feast materialiser -> Redis -> hc.feature_ready
       -> Knative KafkaSource -> Sequence -> KServe predictor -> KafkaSink -> hc.scoring
```

Why each technology was chosen is recorded in the [decisions](/credit-risk-ml-system/decisions/).
